## Codebase Patterns
- Backend follows BaseRepo/ServiceContext pattern
- Routes registered in `backend/src/routes/v0/__init__.py`
- Frontend uses React Query for data fetching with string keys
- Component files named PascalCase, hooks use camelCase with `use` prefix
- Services in `frontend/src/lib/services/` handle API calls
- Entities in `frontend/src/lib/entities/` define TypeScript types
- Pages in `frontend/src/pages/` map to routes in `AppRoutes.tsx`
- Sidebar navigation in `frontend/src/components/drawers/app-sidebar.tsx`
- CronBuilder.tsx already uses "cron" naming internally (for cron expressions) — don't rename cron expression references
- Backend venv for worktrees needs `cd backend && uv venv && uv sync` before typechecking
- The main workspace venv is at `/home/molty/.openclaw/workspace/orchestra/backend/.venv/`
- `service_context.cron_service` field name is defined in `backend/src/contexts/service.py` (renamed in US-002)
- Use `uvx ruff check` for linting when the worktree venv doesn't have ruff installed
- `backend/main.py` also imports the service singleton — don't forget to update it when renaming services
- APScheduler's `SQLAlchemyJobStore` manages its own table (now `crons`, was `schedules`) — not tracked by Alembic metadata
- Migration revision chain: 0000_init → 0001 → 0002
- Use `tsc --project tsconfig.app.json` for typechecking — the root `tsconfig.json` has `"files": []` which checks nothing
- Frontend `CronExecution` uses `cron_id` field (was `schedule_id`), `CronEvent` uses `cron_id` (was `schedule_id`)

  - The `schedules` table is NOT managed by Alembic — it's created by APScheduler's `SQLAlchemyJobStore` on startup via `self.jobs_t.create(self.engine, True)` (creates if not exists)
  - APScheduler creates an auto-named index `ix_<tablename>_next_run_time` on the `next_run_time` column — migration must rename this index too
  - The table has 3 columns: `id` (Unicode(191), PK), `next_run_time` (Float(25), indexed), `job_state` (LargeBinary, NOT NULL)
  - Used `ALTER INDEX IF EXISTS` to handle cases where the index might not exist (e.g., fresh database)
  - Migration revision chain: 0000_init → 0001 → 0002
