## Codebase Patterns
- Wiki is a Docusaurus site at wiki/ (git submodule pointing to ruska-ai/wiki)
- Docs are markdown files in wiki/docs/
- Images go in wiki/static/img/
- Sidebar config in wiki/sidebars.ts
- Changes must be committed inside the wiki submodule first, then submodule ref updated in orchestra
- AGENTS.md is stored as a memory via the memories system; each memory has a `path` (default "AGENTS.md") and `prepare_memory_files()` in `backend/src/agents/__init__.py` injects enabled memories as files into agent context
- Wiki submodule starts in detached HEAD — create a feature branch before committing
- Docusaurus admonitions use `:::tip`, `:::info`, etc. for callout blocks
- Docusaurus links must use relative markdown paths (`../memories/index.md`), not slug paths (`/memories`) — slug paths cause broken link warnings at build time
- Sidebar categories can link to a doc via `link: { type: "doc", id: "agents-md/index" }` making the category label clickable
- App theme toggle has Day/Dusk/Night/System options — must click "Day" for light mode screenshots (not `agent-browser set media light`)
- Clicking model name near chat input goes to Settings page, not a dropdown — model selection is in Settings
- The combobox near the chat input is the assistant selector, not the model selector
- Tool count button next to chat input opens a dropdown with "Upload Photo", "Web Search" toggle, and "Configure Tools" — the latter opens the full Tool Selection modal
- Tool Selection modal has 4 category tabs: Platform, API, MCP, A2A — each with its own panel
- MCP Add Server form has Template dropdown (Custom, Ruska MCP, GitHub MCP), Server Name, Transport (SSE/Streamable HTTP/STDIO), URL, Header Key/Value
- MCP config is saved to user defaults on the backend (not localStorage) via `patchDefaults()`
- Docusaurus image paths for wiki/static/img/ use `/img/...` in markdown (absolute from static root)
- Bot user (im-an-ai-agent) has WRITE on ruska-ai/orchestra but only READ on ruska-ai/wiki — must fork wiki and push there
- Models live in `backend/src/schemas/entities/store.py`, extend `BaseEntity` for persistence
- Update schemas (partial updates) extend `BaseModel` directly with all fields Optional
- Repos extend `BaseRepo` in `backend/src/repos/`, use `(user_id, entity_type)` namespace
- Services are thin wrappers in `backend/src/services/`, registered in `backend/src/contexts/service.py`
- Tools use `@tool` decorator with `ToolRuntime` for user context, registered in `backend/src/tools/__init__.py`
- `_format()` in `base_repo.py` needs extending for new entity types
- `ruff` not installed by default — run `uv pip install ruff` first
- ToolRuntime pattern: `runtime.config["metadata"].get("user_id")` for user context, `runtime.store` for BaseStore
- Helper function pattern: extract `_get_*_service(runtime)` to avoid repeating user_id/store boilerplate across tools
- SearchItem has `.key`, `.value` (dict), `.score` — use raw SearchItems when you need similarity scores instead of model_validate()
- Routes use `ServiceContext(user_id=user.id, store=store)` per request; register in `v0/__init__.py` via `app.include_router(router, prefix=prefix)`
- Frontend entities: TypeScript interfaces in `frontend/src/lib/entities/` matching backend Pydantic models
- Frontend services: static class with static methods, `apiClient` for HTTP, try-catch pattern (see `projectService.ts`)
- Frontend hooks: `useState` for state, handler functions, `useEffectGet*` wrapper for initialization (see `useProject.ts`)
- Frontend contexts: typed with `ReturnType<typeof useHook>`, null default context, `useXContext()` guard hook (see `AgentContext.tsx`)
- SubAgent infrastructure: `SubAgent` TypedDict from `deepagents` with name/description/system_prompt/tools; pass to `create_deep_agent(subagents=...)` for coordinator pattern
- SubAgent dispatch: coordinator agent gets automatic `task(description, subagent_type)` tool via `SubAgentMiddleware`; each subagent is ephemeral (stateless invocation)

## 2026-02-21 - US-002 (Re-verification) + US-003
- Identified root cause of blank tool inputs on /chat streaming path:
  1. First `tool_call_chunk` creates entry with `input: ""` (empty string) → `content` resolves to "" → blank Monaco editor
  2. `in_mem_messages` diverges from React state because `setMessagesState` (not `setMessages`) is used after `formatMessages`
  3. `useMemo([selectedToolMessage])` depends on object reference, not the actual content values
- **Three-part fix applied:**
  1. `Default.tsx`: Return `null` when content is empty — prevents blank dark rectangles entirely. Editor mounts only when content is available.
  2. `Default.tsx`: Changed useMemo dependency from `[selectedToolMessage]` to `[rawInput]` where `rawInput` is derived via nullish coalescing (`??`) outside the memo. This ensures value-based (not reference-based) change detection.
  3. `useChat.ts`: After `setMessagesState(normalizedHistory)`, sync `in_mem_messages = [...normalizedHistory]` to keep the SSE mutation target in sync with React state.
- Browser verified on local dev server (localhost:5174, backed by production API):
  - 5 threads tested: Tokyo, NYC, Berlin, London (multi-tool), San Francisco
  - All Monaco editors display correctly formatted JSON content
  - Read-only confirmed on all editors
  - No blank rectangles observed
  - Multi-tool support works (2 editors in London thread)
- Files changed: `frontend/src/components/tools/Default.tsx`, `frontend/src/hooks/useChat.ts`
- Commit: `b2a8ae5e feat: [US-003] - Fix blank tool inputs on new chat page during streaming`
- **Learnings for future iterations:**
  - `in_mem_messages` is a module-level variable in `useChat.ts` — it's the mutable backing store for SSE streaming. Always keep it in sync with what React renders.
  - `StreamMessageHandler.toolCall()` mutates `in_mem_messages` in-place (push/replace). After `formatMessages()` normalizes, the module-level var must be updated to prevent the next event from operating on stale data.
  - `useMemo` with object reference deps (e.g., `[selectedToolMessage]`) CAN miss updates when the object is a shallow copy (`{ ...msg }`) but the relevant VALUE inside hasn't changed detection-wise. Prefer value-based deps for streaming data.
  - First `tool_call_chunk` from backend typically has `args: ""` (empty string). Plan for empty-initial-then-accumulating pattern in any tool display component.
  - `??` (nullish coalescing) is better than `||` for extracting tool input fields because `""` is a valid (though empty) value — `||` treats it as falsy and falls through.
