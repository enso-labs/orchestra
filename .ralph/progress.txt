## Codebase Patterns
- Tools defined as `@tool` decorated functions in `backend/src/tools/`
- Each tool module exports a `*_TOOLS` list (e.g., `SEARCH_TOOLS`, `FINANCE_TOOLS`)
- Tools registered in `backend/src/tools/__init__.py` via `default_tools()` (no `resolve_tool()` function exists)
- Tags assigned in `backend/src/utils/tools.py` `attach_tool_details()` function
- Tool pattern: accept `RunnableConfig` for user context, use `config["configurable"]` for user_id
- Memory tool at `backend/src/tools/memory.py` — good reference for store-based tools
- Thread search endpoint at `backend/src/routes/v0/thread.py` — `semantic_search_threads()` uses `thread_snapshot_repo.search()`
- `ServiceContext` provides `thread_service` which has `thread_repo` (not `thread_snapshot_repo` — that attribute doesn't exist on ThreadService)
- `ThreadService` singleton pattern: create module-level instance, set `user_id` at call time (same as memory_service)
- `ThreadRepo.search(SearchFilter)` returns `Thread` pydantic models when query is provided, dict otherwise
- Platform tools fetched via GET `/tools` endpoint → `ToolService.tool_details()`
- Frontend `ToolSelectionModal` fetches from `listTools()` in `toolService.ts`
- Frontend platform tools are 100% dynamic from API — no frontend changes needed for new backend tools
