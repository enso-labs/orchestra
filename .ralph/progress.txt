## Codebase Patterns
- Schema fields in `backend/src/schemas/entities/llm.py`: Follow the `subagents` field pattern when adding new list-type fields (Optional with default_factory=list)
- `Assistant.to_llm_request()` must forward all new schema fields to `LLMRequest` constructor
- Pre-existing pyright errors exist in llm.py (None assignments, type variance) — these are not regressions
- `make format` must be run from `backend/` directory, not project root
- Format changes (ruff) may touch unrelated files — include them in commits
- `init_graph()` and `create_deep_agent()` accept `skills: list[str] | None = None` — follow subagents pattern for new params
- Agent construction chain: `construct_agent()` → `Orchestra.__init__()` → `init_graph()` → `create_deep_agent()`
- `stream_generator()` in `backend/src/utils/stream.py` follows subagents pattern for new kwargs — add after `api_key`
- `llm_stream()` in `backend/src/controllers/llm.py` variable `assistant` is actually `LLMRequest` (not `Assistant`) — use `getattr(assistant, "files", None)` for safe access to fields not on `LLMRequest`
- File merge pattern in `stream_generator()`: assistant files as base, request/config files override → `{**(files or {}), **(config_files or input.files or {})}`
- File merge in `llm_invoke()` must happen before `init_backend()` — ToolRuntime reads `request.input.files`
- Worker path in `_execute_agent_stream()`: `files_map` comes from config, merge assistant files before passing to ToolRuntime — same `getattr()` pattern as controllers
- Frontend is loosely coupled to backend API schema — adding new Optional fields with defaults does not break frontend deserialization
- Dev server startup: backend needs `source ~/.env/orchestra/.env.backend`, frontend needs `npm install` per worktree
