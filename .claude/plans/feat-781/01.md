# Separate Tool Inputs and Attach ToolCallId

## Context

Currently, when the LLM streams an `AIMessageChunk` with multiple `tool_calls`, they are bundled into a single message in the chat UI. The `formatMessages()` function merges all `tool_call.args` into a single `input` array on one `AIMessageChunk` message. Tool response messages (`type: "tool"`) already display `tool_call_id` when expanded (in `ToolTimelineItem`), but tool **inputs** don't show their individual `tool_call_id` and are collapsed into one block.

The goal is to:
1. Display each tool input as its own discrete UI element with `tool_call_id`, `name`, and `args` visible.
2. Keep tool response messages displaying their `tool_call_id` (already done).
3. Capture stream logs to understand how tool call chunks arrive for future display decisions.

## Step 1: Split Tool Calls in `formatMessages()`

**File**: `frontend/src/lib/utils/format.ts` (lines 110–160)

Current behavior: AI messages with `tool_calls` get a single merged `input` array.

New behavior: Each `tool_call` becomes its own message in the output array.

```ts
// Current (simplified):
if (message.tool_calls?.length) {
  const input = message.tool_calls.map(tc => ({ ...tc.args }));
  return { ...message, type: "AIMessageChunk", role: "AIMessageChunk", input };
}

// Proposed:
if (message.tool_calls?.length) {
  return message.tool_calls
    .filter(tc => tc.args && (typeof tc.args === "object" || tc.args.trim()))
    .map(tc => {
      let args = typeof tc.args === "string" ? JSON.parse(tc.args) : tc.args;
      return {
        id: tc.id || message.id,        // tc.id is the tool_call_id
        tool_call_id: tc.id,
        name: tc.name,
        type: "tool_input",             // new type to distinguish from tool responses
        role: "tool_input",
        input: args,
        parent_message_id: message.id,  // link back to the AI message
      };
    });
}
```

Note: `formatMessages` currently returns `messages.map(...)` — this needs to change to `messages.flatMap(...)` since one AI message can expand to multiple tool input messages.

**Change**: `messages.map(...)` → `messages.flatMap(...)` at line 99, and return an array from the tool_calls branch.

## Step 2: Update Stream Handler for Per-Tool-Call Tracking

**File**: `frontend/src/lib/utils/message.ts` — `StreamMessageHandler`

Current behavior: `toolCall()` method accumulates all chunks into a single message entry using `toolCallChunkRef` and `toolNameRef` (single refs).

Problem: With multiple concurrent tool calls, a single ref pair can't track them independently.

New behavior: Track per-tool-call state using a `Map<string, { name: string, args: string }>` keyed by `tool_call_id`.

```ts
// Add to StreamMessageHandler:
private toolCallMap: Map<string, { name: string; args: string }> = new Map();

public toolCall(response: any) {
  for (const chunk of response.tool_call_chunks) {
    const tcId = chunk.id || response.id;
    const existing = this.toolCallMap.get(tcId) || { name: "", args: "" };
    
    if (chunk.name) existing.name = chunk.name;
    existing.args += chunk.args || "";
    this.toolCallMap.set(tcId, existing);

    // Find or create a message entry for this specific tool call
    const entryId = `${response.id}-tc-${tcId}`;
    const existingIndex = this.history.findIndex((msg: any) => msg.id === entryId);
    
    let parsedArgs: any = existing.args;
    try { parsedArgs = JSON.parse(existing.args); } catch {}

    const entry = {
      id: entryId,
      tool_call_id: tcId,
      name: existing.name,
      type: "tool_input",
      role: "tool_input",
      input: parsedArgs,
      parent_message_id: response.id,
    };

    if (existingIndex !== -1) {
      this.history[existingIndex] = entry;
    } else {
      this.history.push(entry);
    }
  }
}
```

Also update `toolNameRef` usage in `useChat.ts` for the loading message — use the latest tool name from the map or keep current behavior.

## No Backend Changes

The backend stream already sends individual `tool_call_chunks` per chunk. The separation is purely a frontend concern — how chunks are accumulated and displayed.

## Risks & Considerations

- **Ordering**: Tool inputs must appear in the message list at the position of the original AI message, before their corresponding tool responses. `flatMap` preserves insertion order.
- **Streaming UX**: During streaming, tool input entries will update in-place as args chunks arrive. Each gets its own entry from the start.
- **Checkpoint reload**: When loading from saved thread state, `formatMessages()` handles the split. The saved messages contain the original `AIMessageChunk` with `tool_calls` array — the split happens at render time.
- **Single tool call**: Most common case (1 tool call) still works — just produces 1 `tool_input` instead of 1 `AIMessageChunk`.
