# RLM Integration Strategy for Orchestra

## Context

The Recursive Language Model (RLM) paper (arXiv:2512.24601v2) by Alex Zhang proposes an inference paradigm where LLMs process arbitrarily long prompts by decomposing them, spawning recursive sub-calls in a REPL environment, and synthesizing results. A Python library `rlms` provides a reference implementation.

Orchestra already has SubAgent support, Daytona sandboxes, and LangGraph streaming. The goal is to determine the best integration approach.

## Step 1: Deep Analysis of RLM Library Architecture

**Action**: Clone `github.com/alexzhang13/rlm`, read the source code, and document:
- How `rlm.completion()` orchestrates decomposition
- The REPL environment interface (what methods, what state)
- How recursive calls are tracked and results aggregated
- The prompt templates used for decomposition and synthesis
- How different sandbox backends (local, Docker, Modal) are abstracted

**Output**: Architecture document in this plan file or a separate `analysis.md`

## Step 2: Map RLM Concepts to Orchestra Infrastructure

| RLM Concept | Orchestra Equivalent | Gap |
|-------------|---------------------|-----|
| `rlm.completion()` | `stream_generator()` in `backend/src/utils/stream.py` | Need recursive call support |
| REPL environment | Daytona sandbox (`backend/src/agents/daytona.py`) | Need to bridge RLM REPL interface to Daytona |
| Sub-LM calls | SubAgent via `deepagents` | Already supported; need recursive nesting |
| Decomposition prompts | System prompts / middleware | Could be middleware or agent mode |
| Result synthesis | Final agent response | Need aggregation step |
| Cost routing (big model decompose, small model process) | Model selection per SubAgent | Already supported via `subagent.model` |

## Step 3: Evaluate Integration Options

### Option A: Direct `rlms` Library Integration
- **Approach**: `pip install rlms`, call `rlm.completion()` as alternative to standard LLM calls
- **Pros**: Minimal code; leverage battle-tested library; get updates for free
- **Cons**: Black box; hard to stream intermediate steps to UI; REPL environments may conflict with Daytona; tight coupling to external library
- **Effort**: Low (integration) but High (streaming/UI visibility)

### Option B: LangGraph Native Implementation
- **Approach**: Build RLM as a recursive LangGraph subgraph — decompose node → dynamic worker spawning → synthesis node
- **Pros**: Full control; native streaming; works with existing SubAgent UI; checkpointable
- **Cons**: Must reimplement decomposition/synthesis logic; more code; may miss paper optimizations
- **Effort**: Medium-High

### Option C: Hybrid — rlms Engine + LangGraph Streaming
- **Approach**: Use `rlms` for decomposition logic but wrap each step as a LangGraph node, streaming through the existing pipeline
- **Pros**: Best of both — paper's algorithms + Orchestra's streaming/UI
- **Cons**: Complex adapter layer; version coupling; two systems to maintain
- **Effort**: High

### Option D: Tool-Based Exposure
- **Approach**: Expose RLM as a tool the agent can invoke when it detects large input (similar to existing skill but platform-level)
- **Pros**: Simplest; agent decides when to use it; no core architecture changes
- **Cons**: Agent must be smart enough to invoke it; less integrated UX; no streaming of recursive steps
- **Effort**: Low
