## Key Findings

### 1. Latency: 2.5x Overhead

RLM took 76.5s vs 30.4s for standard completion — a 2.5x slowdown. The overhead comes from:
- 12 iterative REPL cycles (LM generates code → execute → format results → repeat)
- 20 sub-LM calls to gpt-4.1-nano for chunk analysis
- Sequential TCP socket communication for each sub-call

**For inputs within the context window** (like our 50k char test), standard completion is faster and cheaper. The RLM approach becomes valuable only when inputs **exceed the context window** and standard completion fails entirely.

### 2. Cost: 7.4x Higher

RLM cost $0.054 vs $0.007 for standard — a 7.4x increase. The cost amplification comes from:
- **Root model overhead**: 12 iterations of gpt-4.1-mini processing the growing message history (iteration results accumulate)
- **Sub-model bulk**: 20 calls to gpt-4.1-nano for chunk analysis
- **Token amplification**: 126k input tokens vs 10.6k — the REPL loop context grows with each iteration

The dual-model approach helps (nano is 4x cheaper than mini), but the iterative context growth is the dominant cost factor.

### 3. Quality: Comparable but Different

Both approaches produced structured, relevant analysis. Differences:

| Dimension | Standard | RLM |
|-----------|----------|-----|
| Completeness | Covered all 3 areas thoroughly | Covered all 3 areas |
| Depth | Specific code references (file:line) | More general observations |
| Structure | Single cohesive report | Aggregated from sub-analyses |
| Accuracy | Identified specific patterns | Identified same patterns at higher level |
| Response length | 9,283 chars (longer) | 5,998 chars (more concise) |

Standard completion produced a more detailed response for this input size because it could read the full context directly. RLM's advantage would emerge with larger inputs where standard completion truncates or fails.

### 4. FINAL_VAR Bug: Response Extraction Inconsistency

During testing, one RLM run returned only the variable name `"final_report"` (12 chars) instead of the variable's contents (~6k chars of analysis). This happened when:
- The LM used `FINAL_VAR(final_report)` to signal completion
- The library's `find_final_answer()` executed `print(FINAL_VAR('final_report'))` in the REPL
- But the variable resolution sometimes returns the name instead of the value

This is a known limitation of the rlms library (v0.1.0) — the `FINAL_VAR` extraction depends on environment state that can be inconsistent between iterations. The LM sometimes stores results in variables that go out of scope.

**Impact**: Unreliable response extraction is a production blocker for direct rlms integration.

### 5. Streaming: Confirmed Blocker

RLM's `completion()` blocked for 76.5 seconds with zero intermediate output. The verbose mode showed rich iteration progress (decomposition plan, code execution, sub-call results), but this information is only available to the console logger — not as programmatic callbacks.

**Confirmed**: The streaming gap identified in `docs/rlm-recommendation.md` (Gap 1) is real and critical.

### 6. Sub-Call Parallelism: Works

The 20 sub-LM calls to gpt-4.1-nano used `llm_query_batched()` internally with `asyncio.gather()`. This is the key speed benefit — without batching, the 20 sequential calls would have taken ~40s instead of ~10s.

## Implications for Orchestra Integration

Based on these results, the integration recommendation from `docs/rlm-recommendation.md` is validated:

1. **Option A (Direct rlms)**: Confirmed as non-viable for production due to:
   - No streaming (76s blocking)
   - FINAL_VAR response extraction bugs
   - 7.4x cost overhead for within-context inputs

2. **Option D (Tool-Based)** remains the recommended approach because:
   - Full streaming via standard LangGraph tool calls
   - Reliable response capture (no FINAL_VAR issues)
   - Cost controlled (agent decides when to decompose vs. process directly)
   - The `batch_llm_query` tool provides the key parallelism benefit

3. **For inputs within context window**: Standard completion is better in every metric. RLM should only activate for inputs exceeding the model's context window.

4. **The existing `.claude/skills/rlm/SKILL.md` pattern** (Sonnet supervisor + parallel Haiku workers) already implements the optimal approach — it just needs to be ported to the backend agent pipeline.
